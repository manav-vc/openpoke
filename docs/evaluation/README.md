# Evaluation results

The November 16, 2026 checks use real `anthropic/claude-sonnet-5.5` models and `openai/text-embedding-3-small` embeddings with synthetic email tools. They evaluate task outcomes, source-assisted recall after real compaction, and routing among similar saved tasks. **No live Gmail mailbox is accessed.** Original failed and incomplete attempts remain visible alongside later results.

The final offline suite passed **196 tests**, with four existing FastAPI lifecycle deprecation warnings.

## Fixed outage handling

The original **9/10** run below exposed a runtime bug. After handling a read-only email outage, the model reported `needs_review`; the runtime treated that as an uncertain external action, interrupted the job, and blocked subsequent work on the EA. The source trace shows only read effects, so this was a false recovery lock, not merely a scoring mismatch.

The model can now report `open` or `waiting_for_user` for unavailable information. Only runtime effect tracking can establish `needs_review`; uncertain writes still use the existing recovery path. Regression tests replay both returned read errors and raised read exceptions, preserve the failed source result, and verify that a same-agent follow-up runs. The subsequent live outage case reports the failure without guessing and ends normally. The original failed report is unchanged.

Every probe requires the exact structured facts, retrieval and citation of the necessary original events, no invented citation IDs, no attempted write, and preserved pending approval. Context values are conservative estimates, not measured savings in provider prompt tokens across all model calls.

The live work exposed a weak summary prompt: it did not state the saved token budget and could enumerate routine updates until output was truncated. The production prompt now states that budget, prioritizes corrections, identifiers, approvals and source IDs, and groups routine traffic. Earlier output-limit, token-budget, response-format and credit-blocked attempts are retained. An earlier 3,500/800 stress run changes from 1/4 to 4/4 under a disclosed JSON-extraction correction; this is an offline diagnostic rescore of the same answers, not a new run or the production-default result above. Requested JSON fields are scored; surrounding prose is not graded.

## Dense retrieval and final routing

[retrieval-hard-results.json](retrieval-hard-results.json) uses **288 plausible invoice agents**: 12 contacts with 24 invoices each, overlapping descriptions, shared threads, changed instructions and archived work. There are 36 queries, comprising 34 labeled targets and two intentionally ambiguous requests. All vectors were generated by the real embedding model, with zero indexing backlog.

| Ranking mode with the same identity guards | Recall@10 | Recall@30 |
| --- | --- | --- |
| Hybrid | 34/34 (100%) | 34/34 (100%) |
| Keyword only | 24/34 (70.6%) | 34/34 (100%) |
| Semantic only | 34/34 (100%) | 34/34 (100%) |

On the 16 paraphrase cases, keyword recall@10 was 9/16 and hybrid was 16/16. Archived paraphrases were 1/4 and 4/4 respectively. Exact identifiers bypass ranking in every mode; those cases measure identity resolution, not embedding superiority. There were no identity-conflict or ambiguity-guard failures.

Four additional turns ran the production IA/EA loops, queue and delivery over the dense corpus: **3/3 correct owner selections and 1/1 clarification**, with no duplicate agents or unapproved action. The original workflow score was 3/4 because `1,180` failed a literal `1180` check. The export preserves that result and all original checks; explicit numeric normalization gives 4/4 without changing any answer or making another model call. Superseded amounts are checked separately. The live evaluation used 48 provider calls and US$0.181006.

This corpus supports a first-page recall improvement over keyword search. It **does not show hybrid outperforming semantic-only retrieval**. Hybrid remains a practical design choice for literal references, paraphrases and degraded operation; the measured limits and untested alternatives are explained in [the implementation rationale](../agent-optimization.md).

## Controlled upstream comparison

[upstream-comparison.json](upstream-comparison.json) retains the paired evidence and earlier failed attempts. Both implementations receive the same model, nine scenarios / ten user turns, five saved tasks plus 40 distractors, and synthetic mailbox records. Upstream is unmodified application source at `5b5f635935a64ab37884c025d70abb0ed731c094`, with its model setting injected to match the fork. Native prompts, tools, history construction and agent loops differ as intended.

| Final paired observation | Upstream | Fork |
| --- | --- | --- |
| Shared workflow checks passed | **6/10** | **10/10** |
| Unexpected EA dispatch turns | 1 (ambiguous request) | 0 |
| Duplicate EAs | 0 | 0 |
| Turns without an unapproved send attempt | 10/10 | 10/10 |
| Provider-reported chat prompt tokens, all IA/EA calls | 570,500 | 394,128 |
| Median workflow latency | 15.22 s | 22.03 s |
| Model/embedding requests with provider errors | 0 | 0 |
| Provider-reported cost, including indexing | US$1.294630 | US$0.917452 |

The fork passed all native approval and exact-draft checks too, including the repaired unavailable-email case. In this run it used **30.9% fewer chat prompt tokens**, while its median workflow latency was **higher**. Additional discovery and inspection calls have a latency cost; the observation is not evidence that the fork is universally faster or cheaper. Token totals include all per-turn calls, including upstream's unsuccessful interaction loops.

Both implementations selected the correct existing saved owner in **8/8 applicable turns**. The upstream unexpected-dispatch count comes from the intentionally ambiguous request, not wrong reuse on a specified invoice. Including new-agent creation, owner/creation checks were 8/9 upstream and 9/9 in the fork. The three final funded evaluations (upstream, fork and memory) reported **US$2.475670** combined usage.

Upstream's four shared-contract failures have different meanings. Two interactions exhausted the native eight-iteration loop after correct drafts and previews had already been produced; these are control-flow failures, not wrong invoice facts. The ambiguous request dispatched two EAs and produced a combined draft instead of clarifying first. New work produced a correct IA text preview, but did not create an EA-owned email-tool draft. The latter fails the selected persistence contract and does not mean the text was incorrect.

The shared contract requires correct task reuse, facts, an EA-owned persisted email-tool draft where requested, relevant clarification without premature dispatch, and no attempted send. An IA-only text draft does not satisfy that persisted-draft contract. Exact draft presentation and the fork's additional persisted approval metadata are reported separately. Read-only answers from verified saved sources can pass without redundant execution. See the artifact for per-turn checks, actions, usage and implementation differences.

Latency includes interaction, execution and result delivery, excluding embedding setup and refresh. Setup usage is recorded separately. These are small authored runs, not a production reliability estimate or proof of a general speed or cost improvement. Earlier interrupted transport, credit and harness attempts are never pooled into a clean run's totals. The pre-top-up fork run was 9/10 due to two provider read errors; the original outage case passed. Later HTTP 402 attempts and an upstream observer/Windows-cleanup failure are retained separately. The corrected observer preserves multiline draft previews; the earlier missing-preview scores are not treated as a product defect.

## Evidence and reproduction

[live-workflows.json](live-workflows.json) preserves both reports' summaries, original per-turn checks, queue outcomes, usage, timestamps, model IDs, source/fixture hashes, and hashes of the raw reports and call journals. It is a selected-field export, not a rescore. Raw reports remain at the recorded paths under ignored `server/data/evaluations/`; the shareable export lives here so it can be versioned. Earlier smoke, blocked, and incomplete attempts are excluded from these full-suite totals.

Both historical runs recorded source hash `93275d3d1723b6dafb7d42ffb21c7cbc983fa1c9a5d533d790b573d105e5552c`. Their working tree included uncommitted changes. The current code has subsequent runtime and summary-prompt fixes, so new reports identify their own evaluated source. Chart-script changes also affect the original evaluator's directory-wide hash.

To repeat the full suite from the repository root, using the project environment and an OpenRouter key:

```powershell
python tests/evaluation/evaluate_agent_workflows.py --live --model anthropic/claude-sonnet-5.5 --max-calls 150 --max-tokens 750000 --max-cost-usd 2.00
```

These explicit limits match those recorded in both reports; the default token budget is smaller than either run's usage. This command makes billable requests and writes a new report. See [the evaluator guide](../../tests/README.md#real-model-workflows) for setup, scoring, and controls.

These two historical runs do not establish production reliability. Reply and clarification checks use word matching. Real Gmail behavior, nested email-search model quality, restart recovery and scheduler behavior remain outside the live evaluation. The [before/after overload charts](../charts/README.md) use separate offline measurements; the new memory experiment above evaluates source-assisted recall after generating real summaries.
